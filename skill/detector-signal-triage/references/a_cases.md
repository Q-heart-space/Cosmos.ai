# 判例库 + 高频缺陷模式

### ⚠️ 反面判例（2026-09-02·我判错了）

`consumer_check --full-wiring` 报 7 个 P0「声明 N 消费者·缺 1」。

- **我的误判**：定性为「② 口径缺陷·反模式#45」，理由是「检测器扫不到函数级导入 `from X import sense` 和 argv 拼接形态」→ 建议**增强检测器**。
- **真相**：`expected_consumers` 语义是 incoming。7 项里 1 项**方向倒置**（`dam_neural_system.py:57` 是它**调用** sensor，却声明「sensor 消费我」），6 项**零关联误声明**（双方代码全文无对方标识）。
- **后果**：若照我的方案改检测器 → 掩盖真实缺陷，并**亲手制造**反模式#45。
- **正确处置**：移除 7 项误声明 → `P0 7→0 · passed 534→541`。
- **错因**：我验证了「文件是否存在」「有没有代码引用」，**唯独没验证方向**。

> **教训**：判「检测器错了」的举证责任在**你**。改检测器 = 让温度计闭嘴；改声明 = 让室温回归真实。二者都可让报警消失，但只有一个是对的。

## 🆕 Step 0.5：同文件自证 + 文档/代码双向验（2026-09-02）

两次实证表明，判"检测器错"之前还有两步更快、更硬的验法。

### (a) 同文件自证：先在同一文件内找矛盾

检测器不是"客观事实"，它只是**另一份被人工维护的规范副本**，内部就可能自相矛盾。

**铁证实例**：`preflight_check.py` 中——
```python
CONSTITUTION_FILES = [("constitution/跨空间本体论.md", ...)]   # 宪法在 constitution/
NAMING_POLICY = {'🏛️': {'dirs': ['']}}                          # 宪法必须在根目录
```
**同一个文件里两处打架** → 无需外部推理即可判定规则陈旧。

> **做法**：拿到报警后，先在检测器文件内 grep 同一个概念的所有出现点，看是否自洽。同文件自相矛盾 = 最硬的证据，优先级高于任何外部论证。

### (b) 文档缺陷与代码缺陷互为掩护

**机制**：文档写错 CLI → 该代码分支从未被成功触达 → 分支内的缺陷长期不可见。

**实证**：规范 4 处写 `--check naming <file>`（位置参数），实跑被 argparse 拒绝 →
`--check naming` 全量分支**从未执行** → 其调用 `check_naming_compliance(ROOT)` 的 **NameError（该函数从未定义）潜伏至今**。
打通 CLI 后，代码缺陷立即暴露。

> **做法**：
> 1. **文档里的命令必须实跑**——`--help` 只证明参数存在，不证明调用形式合法。
> 2. 修好一处后**立即复跑被它挡住的整条链**，而不是只验证刚改的那一处。
> 3. 判"这个功能没人用"之前，先确认**它是不是根本跑不起来**。

### ⚠️ 反面判例 2：对照实验方法失效（2026-09-02·我差点误判）

为验证「2 个 ERR 是否自己引入」，我把 v1.10 备份放到 `.workbuddy/_probe/` 下对照，得到"v1.10 无告警"→ **一度差点判定"ERR 是我引入的"**。

实查后是对照方法失效：
```python
ROOT = Path(__file__).resolve().parent.parent
# __file__ = .workbuddy/_probe/preflight_v110.py
# parent.parent = .workbuddy   ← 不是 Q博士
```
→ `relative_to(ROOT)` 抛 `ValueError` → 崩溃 → 输出被 `grep` 过滤后看起来像"无告警"。

> **教训**：**对照结果与预期不符时，先怀疑方法，再怀疑结论。**
> 自检清单：① 被测脚本的 ROOT 是否正确？② 依赖模块能否导入（PYTHONPATH）？③ 是否过滤掉了 traceback？④ 崩溃与"通过"在过滤后长得一样——**永远先看原始输出，别只看 grep 之后的结果**。

## 🆕 Step 0.6：闭环最后一公里——回头看自己的产物（2026-09-02）

首轮验证通过 ≠ 闭环完成。首轮验证通常只覆盖「**规则是否一致**」，漏掉三个维度：**版本号**、**统计口径**、**约束方向**。这三类会原样复发在**你刚交付的文件上**。

**必查三项（写完自己的交付物后）**：

| 维度 | 常犯错误 | 检查手段 |
|:--|:--|:--|
| **版本号** | 依赖声明里写的版本，落后于被依赖文件的实际版本 | 所有引用了版本号的文件，逐个比对头部版本 |
| **统计口径** | 用「目录内文件数」代替「该类型文件数」 | 按**类型字段**重新计数，与目录 `ls` 结果对账 |
| **约束方向** | 只写了单向约束（A 须在 D），漏了反向（D 内不得有非 A） | 对每个目录约束，自问「反过来是否也成立、是否也写了」 |

**反面判例 3：闭环后回头看，连挖三层**（2026-09-02 同一轮内）：
1. 第一层——发现自己的检测器依赖行写「规范 v1.148」，而规范已 v1.149（版本号漂移）。
2. 第二层——修完复验时，自检用 `in` 子串判断残留，命中了**自己刚写的修复注释** → 假报「有残留」（经验㊸ 当场复发）。
3. 第三层——为核实「合规=17」这个数字，按**类型字段**重新统计 → 实为 🏛️ 16 + 📋 1，首轮把 16 误报成 17，且错误已写进「一句话结论」。

三层全部源自同一动作：**闭环结束后又回头看了一眼自己的产物**。

> **判定口诀**：首轮验证回答「我改的对不对」；回头看回答「我还有哪里没看」——后者才决定闭环是否真的闭合。

## 已知高频缺陷模式（实证判例）

| 模式 | 判例 |
|:--|:--|
| 字段定义但**未参与计算** | cost_matrix_analyzer 的 `failure_consequence`（只在输出展示）→ 漏算风险维度 → 3/7 假反转 |
| 正则只匹配**带后缀**形态 | `re.findall(r'(\w+\.py)')` 漏 `from header_parser import`（无 .py）→ 16 处引用被判孤立 |
| 路径**拼接形态**匹配不到 | `ROOT / "scripts" / "X.py"` 拼接 → grep `scripts/X.py` 失败（closure 检查器组/write_guard 级联链同源） |
| **只读前 N 字符** | `content[:5000]` → 漏文件中后部引用 |
| **信号不可得 → 默认 0 分** | l5 Phase3 章节消失 → `completion_pct` 缺失 → 10% 权重恒 0（假零） |
| **真相源分裂** | wiring_map.lifecycle=tool（36）vs tool_whitelist.json（29）→ 仅重叠 7 |
| **早退分支丢标志** | `if total_weight == 0: return {"score": 0}` —— 丢失 available/details |
| **检查器导入期崩溃（反向假拒/假红）** | 门禁/检测器在模块 import 阶段抛异常（如 constrained 子进程缺 `HOME`/`USERPROFILE` 致 `Path.home()` 崩溃）→ exit=1 → 下游 fail-closed **误拒所有合法输入**（假红，与"假零"对称：假零漏判真问题·假红误杀合法） |
| **声明方向倒置 / 零关联误声明** | `expected_consumers` 语义是 incoming（谁消费我），却填了 outgoing（我调用谁）或同类清单 → 检测器判 miss。**检测器是对的**（属③真问题）。2026-09-02 实证 7 例 |
| **信号不可得→默认拒（fail-closed 反向）** | 检查器自身崩溃 → 红灯信号全不可信 → 须先确认检查器可在真实执行环境加载，再判报警性质 |
| **检测器内部自相矛盾** | 同文件两处定义打架（`CONSTITUTION_FILES` 用 `constitution/` vs `NAMING_POLICY` 用根目录）→ 规则陈旧，报警为误报。2026-09-02 实证 |
| **文档 CLI 失效掩盖代码缺陷** | 文档写错调用形式 → 分支从未执行 → 分支内缺陷（NameError）不可见。修 CLI 后立即暴露。2026-09-02 实证 |
| **检测器口径落后于配置源** | `preflight` v1.10(07-14) 落后 `directory_registry` v1.4(08-24) 约 50 天 → 同名概念两套判定。2
| **规则只约束单向（目录纯度）** | 规范只写「A 类文件须在 D 目录」，未写反向「D 目录内不得混入非 A 类」→ 检测器能发现「放错地方」，发现不了「混进来」。2026-09-02 实证：`constitution/` 17 个 .md 里混入 1 个 📋 类型文件（综合工作规划.md），无任何检查项报警 |
| **崩溃与发现问题同形退出码 → 合法化洗白（假绿）** | 检查器崩溃 exit=1 落入 `known_exit_codes=[1,2]` → 计为成功·健康度虚高（asset_health_check UTF-16 判例·2026-09-06）。锚点：术语表 #310·META-1553 |
| **产出/渲染环节崩溃 → 结果隐身（假绿）** | 守卫已执行且已检出，输出异构结构致 `KeyError` → 结果不可见（argparse_signature_auditor 判例·2026-09-06）。与「导入期崩溃」差一层：执行了但没产出。锚点：术语表 #309 ②子型·META-1554 |
| **红灯主键来自执行空间 → 不可反查** | 失败记录以运行时序号（「L3: 快速维护(<30s)-21」）为标识、命令串截断 60 字符 → 无法反查 `known_exit_codes`/`timeout` → 只能重跑复现（43 条·16m50s·2026-09-06）。锚点：术语表 #311·META-1555 |
| **提示器恒报警（不可清零）** | 检测器用**长度截断**提取概念名（`[:12]`）→ 「崩溃被合法化——检查器崩」永远命中不了真相源 → 概念已登记仍报未注册（4 例实测·2026-09-07）。恒报警的提示器比没有提示器更糟：**真信号被恒定噪音淹没** |
| **检测器存在但跑不完（僵尸功能）** | 实证耗时 401.2s > 预算 390s → 每轮超时中断 → 从未完整运行 → 与「参数错误 exit=2」同为僵尸两死法（2026-09-06 双例） |
| **派生清单指纹无门禁（自反身性盲区）** | 能力清单（`qdr_capability_neutral_manifest.json`）的 `version`/`artifact_sha256_prefix` 不随 SSOT 制品自动更新，且 `standard_bridge --verify-neutral-manifest` **只校验状态字段、不校验版本与指纹** → 改了技能后清单静默漂移，**无任何检测器报警**。2026-09-07 实证：本技能 v1.6→v1.7 后三宿主已同步（指纹一致），清单仍记 `1.6`/旧指纹；同轮内二次编辑后清单**再次**漂移。**判据：改 SSOT 制品 = 必须同步所有派生清单，并手工核对指纹**（反模式#56 级联同步体系漂移同源） |
| **统计口径用目录代替类型字段** | 数「某类型有几个」时按 `ls D/ \| wc -l` 计数，而非按头部**类型字段** → 目录内文件数 ≠ 该类型文件数。本次把 16 误报成 17，且错误一路带进「一句话结论」 |026-09-02 实证 |
