# 检测器红灯三分法

## 何时用

任何检测器报出异常值（红灯·0 分·CRITICAL·孤立项·不等式反转）时——**先分诊，后治理**。
直接按报警值去"修复被报警的对象"，十次有七次是在修假问题。

## 核心判据：三类性质

| 类别 | 特征 | 识别方法 | 处置 |
|:--|:--|:--|:--|
| **① 模型缺陷** | 度量模型漏算了一个维度 | 读计算函数：字段定义了但**从未参与计算**（只在输出时展示） | 补齐缺失维度·保留原值对照 |
| **② 口径缺陷** | 检测器实现漏查某种引用/触发形态 | 找出该检测器的"可达集"由几个源构成·逐个验证形态覆盖 | 补源 / 改单一真相源 |
| **③ 真问题** | 排除前两者后仍成立 | 三者排除法 | 正常治理·记录待办 |

## 标准流程（9 步）

-1. **🆕 信号源可信度四分**（见 Step -1 节）——红灯可反查吗(④)？检测器崩在导入期(①)／产出期(③)／被合法化洗白(②)？**此步不过，禁止进入 0**
0. **🆕 先验证语义方向**（最易错的一步·见下节）—— 声明的箭头指向谁，谁的代码里就该有对方的名字
0.5. **同文件自证 + 文档/代码双向验**（见 references/a_cases.md）——先在检测器文件内 grep 同一概念找自相矛盾；文档命令必须实跑
0.6. **闭环最后一公里——回头看自己的产物**（见 references/a_cases.md）——版本号 / 统计口径 / 约束方向三项必查
1. **读检测器的计算函数**（不是读输出）——确认每个字段是否真参与运算
2. **列出可达集构成源**——调度源（automation/daily_tasks/write_guard/closure）+ 依赖源（import）+ 豁免源（whitelist）
3. **逐个形态验证**——每种引用形态都实测一个样本（如 `from X import` 不带 .py 后缀 vs `scripts/X.py` 字符串）
4. **核查真相源唯一性**——同一语义是否有 N 个文件各存一份（wiring_map.lifecycle vs tool_whitelist.json 实证仅重叠 7/36）
5. **真孤儿才治理**——逐个判定：接线 / 标注 tool / 归档

## 🆕 Step 0：语义方向验证（最易误判的一步）

**口诀**：声明的箭头指向谁，**谁的代码里**就该有对方的名字。

任何形如「A 声明了 B，但检测器在 B 里找不到 A」的报警，**在怀疑检测器之前必须先验方向**。
`expected_consumers` / `depends_on` / `consumed_by` 这类字段都有**方向性**：

| 字段语义 | 正确填充 | 错误填充（倒置） |
|:--|:--|:--|
| incoming「谁消费我」 | 那些**代码里引用了我**的脚本 | 我调用的那些脚本（outgoing） |
| outgoing「我调用谁」 | 我代码里引用的脚本 | 那些引用了我的脚本 |

**验证三步**：
1. 确认字段语义是 incoming 还是 outgoing（读检测器判定代码，不要靠字段名猜）
2. 反向验证：被声明方**自身**的同类声明是否成立？（若 B 自己的声明全通过，说明 B 的接线是健康的，问题在 A 的声明方向）
3. 零关联验证：`grep` 双方代码是否含对方标识。若 A 调用 B 却声明「B 消费我」→ **方向倒置**；若双方代码零关联 → **误声明**

**判据**：方向倒置 / 零关联误声明 = **③ 真问题**（改声明，不是改检测器）。

## 🆕 Step -1：信号源可信度四分（2026-09-07 重构·前置门禁）

> 三分法假设「检测器能跑且信号可信」。**这个假设本身必须先被验证**。
> 本步在「读计算函数」**之前**执行——信号源不可信时，后续所有分诊结论一律无效。

| # | 失效形态 | 失真方向 | 表现 | 判别信号 | SSOT 锚点 |
|:--|:--|:--|:--|:--|:--|
| ① | **崩溃 → fail-closed 误拒** | 假红（**误杀**） | 绿灯放行变红灯拒绝 | 检查器在 **import 期**崩溃（`Path.home()`/`expanduser` 依赖宿主环境变量）；或**判据字面化**——只认裸露值形态、不认合法书写形态（如 YAML 引号 `version: "2.0.0"`）→ 合法项被判缺失（RC-058·2026-09-07） | 2026-09-01 判例 + ①b 判例（下） |
| **①c** 🆕 v1.12 | **判据前提假设失效 → 误拒**（⚠️ 且**连带损害**） | 假红（**误杀**）+ **处置动作破坏他方数据** | 合法操作被判失败；**更严重**——失败后的「回滚/补偿」动作会覆盖他方已写入的合法内容 | 判据含**未被声明的环境假设**（如 `verify_write` 假定「写入窗口内无第三方写」）；在并发环境中该假设被违反 ⇒ 把「**他方并发写入**」误判为「**我写入失败**」（T-24·2026-09-18）；判别问句：*「我的判据依赖了哪条我从没写下来的环境假设？」* | 2026-09-18 判例（`a_signal_credibility.md` ①c） |
| **①d** 🆕 v1.13 | **检测域未判定 → 误杀** | 假红（**误杀**）+ **豁免集逐条代偿**（隐性技术债） | 规则**名称 / 自陈语义**指向的对象类别 ≠ 判据**实际覆盖**的对象类别 | 判别问句：*「这条规则的**名字**说要检查什么对象？`source_pattern` / 判据**实际**覆盖了什么？」*——不一致即命中（实证：A2 规则名 `📘制度→综合规划+DAM`，而 `source_pattern=^governance/.*\.md$` **无类型过滤** ⇒ 26 个 📋/📜/📐 文件被误纳·10 项缺口全属误报）；**温度计信号**：豁免集条目数≈「检测域内非目标对象数」⇒ 已在用逐条补丁代偿判据缺失（`A2_INDIRECT_EXEMPT` 积累 **60+** 条即此症） | 2026-09-18 A2 检测域收窄判例 |
| ② | **崩溃 → 被合法化** | 假绿（**洗白**） | 崩溃却计入成功·健康度虚高 | 「崩溃」与「发现问题」**返回同一退出码** + 存在 `known_exit_codes` 类合法化机制 | **术语表 #310 崩溃被合法化**·META-1553·反模式 #101 |
| ③ | **执行并检出·产出环节崩** | 假绿（**隐身**） | 守卫真跑真检出，但结果不可见 | 输出「检出 N 项」后紧跟 traceback；或结果结构异构致渲染 `KeyError` | **术语表 #309 假通电·②产出层崩溃子型**·META-1554 |
| ④ | **记录主键不可反查** | **不可治理** | 红灯存在但定位不到配置真相源 | 主键=运行时临时序号（如「L3: 快速维护(<30s)-21」）或命令串被截断 | **术语表 #311 取证稳定主键**·META-1555 |

> 🔗 四态实证判例见 references/a_signal_credibility.md（① 2026-09-01 崩溃误拒·①b RC-058 判据字面化·② UTF-16 合法化·③ argparse 产出层 KeyError）。

> **SSOT 纪律**：以上四态的**概念定义以核心概念术语表为准**（#309/#310/#311·均为候选登记态）；META 编号指向元模式库实证全文。本技能**只放分诊判据，不复制定义**——防第二真相源（铁律X）。

**第一原理**：退出码是**语义有损信道**。同一码位承载「崩溃」与「发现问题」两种语义时，任何基于退出码的聚合都会系统性失真，且**失真方向恒定偏向「健康」**——合法化只能在同一语义层做，不能跨层混用。

**处置顺序（不可跳过）**：

1. **先判 ④**——这条红灯**可反查**吗？主键须来自**配置空间的稳定 id**（`task_id`），而非**执行空间的临时序号**。不可反查时先补主键再分诊（实证：43 条日治失败因主键缺失，逐条重跑复现耗时 **16m50s**——不可反查的红灯，处理成本从「读一条记录」放大到「重跑一次」）。
2. **再判 ①②③**——信号源本身可信吗？三者均属**机制缺陷**：**修检测器，不修被报警对象**。
3. **全部通过后**才进入下面的三分法（模型缺陷 / 口径缺陷 / 真问题）。

**🆕 ①d 修法（检测域未判定 · 口径缺陷的根因级修法）**：口径缺陷的**根因级**修法**不是「加豁免」**，而是三步——

| # | 步骤 | 内容 | 反面（反模式 #44「只修数据不修判据」） |
|:--|:--|:--|:--|
| 1 | **检测域判定** | 检查器**先判定「我的检查域」再判定「对象是否合规」**；域外对象 **skip**；**禁止用默认目标兜底**（v1.17 A5 确立·v1.18 A2 复用） | 默认全量纳入 ⇒ 靠豁免集逐条捞 |
| 2 | **共享提取（铁律X）** | 判据谓词提取为 **SSOT**（如 `sync_audit.a2_in_domain()`），**全部消费者 `import` 复用**；**禁止各自实现** | 三处各写一份 ⇒ **口径漂移**反复复发 |
| 3 | **门禁强度不降自证** | 必须给出「收窄后**新增缺口 0 项**」的反面证据；**仅「明确非目标」才 skip · 读不到标记一律保守受检** | 收窄顺带放宽 ⇒ 真问题漏判 |

> **判别捷径**：**豁免集的条目数**是缺陷规模的**温度计**——豁免集条目数接近「检测域内非目标对象数」时，即已用「逐条补丁」代偿「判据缺失」。
> **反向自检（对称于 RC-058）**：收窄检测域时须反向问——「**我的 skip 会不会把真问题也放过？**」→ 故 skip 只对**明确标注的非目标**生效，**判定失败/标记缺失一律回到受检**。

**⛔ 反直觉点**：① 让报警**变多**（误杀合法），②③ 让报警**变少**（漏判真问题）。二者都能让报警数字变化，认错方向就会反向修复。

**🆕 守卫反向自检（RC-058·2026-09-07·防「治假绿时造假红」）**：新增/修复守卫后，**必须反向问一句**——「**合法形态会不会被我误判？**」

| 自检问句 | 判据 | RC-058 实证答案 |
|:--|:--|:--|
| ① 字面还是语义？ | 判的是**字面形态**还是**语义等价**？合法书写变体是否都覆盖？ | 错：只认裸露 `version: 2.0.0`，不认 `version: "2.0.0"`（语义等价但字面不同） |
| ② 误报可量化吗？ | 能否给出**误报率**而非「看起来对」？ | 3/63 = 4.8%（全量 63 个 SKILL.md 实测：带引号 3 / 不带 60 / 无 version 0） |
| ③ 捕获边界对吗？ | 变体标记（引号/空白）放在捕获组**内**还是**外**？ | 修复时须置于捕获组**外**，否则捕获值含引号→引入新假红 |

> **结构性教训**：守卫刚被要求「不要漏报」时，往往同时变得「**过度敏感**」。故**守卫本身必须与被测对象同受 Step -1 检验**——检测器不是免检区（反模式 #63 覆盖检测维）。


## 防粉饰铁律

修复检测器后数值变绿，**必须能回答**：
- 变绿是因为**补齐了缺失维度**（模型修正）还是**调低了阈值**（粉饰）？
- 是否保留**原始值对照**（base vs adjusted）？
- 是否**真跑验证**（非仅语法通过）？
- 🆕 修复后**该提示器能否归零**？（不可归零 = 检测器自身缺陷未除·假闭环）
- 🆕 修复后**该红灯能否被反查到配置源**？（不可反查 = 下次仍要重跑复现）

## 自进化机制（盲区驱动循环 · 技能自进化 #345）

> 本技能是**枝·防御**层高频引用技能——判断红灯性质的经验随实践持续进化，故按下述机制吸收反馈、避免僵化：

1. **反馈吸收**：每次真实分诊（含假红/假绿判定）结束，将结果回写本节判例来源（日期+实证文件）；误报类反馈优先参考 `governance/data/detector_feedback.json`（`detector_feedback.py --list --detector <名>`）——误报实例是规则盲区的最精确揭示
2. **经验库沉淀**：新判例进入「已知高频缺陷模式（实证判例）」表 + 锚点 META 编号；结构分层后扩展判例移入 references/（渐进披露）
3. **自适应校准**：判定规则出现反例（如新假红类型）→ 先归并已有反模式/META（防造新词），确属新维度才新增判例行
4. **迭代留痕**：每次修订 bump version + 变更历史行 + 记流程日记（2026-09-10 起）

> **验收**：skill_self_evolution_check.py --skill detector-signal-triage ≥ EVOLVING（4 判据全过）。

> 🆕 v1.11（2026-09-10·全链路审计驱动的自进化补齐·反模式 #45）

- **盲区①·本技能不产出可执行检测器**：本技能是**人工分诊方法论**（何时用三分法/四分法），自身不生成检测器脚本。
  **漏检场景**：只走流程不落门禁 → 分诊结论随会话消失（**无留痕**）·同一假红判据在多个技能各自重复踩坑。
- **盲区②·判据的代码实现可能偏离判据语义**：本技能教导「先判定报警性质」，但**判据实现**若用
  **字面词表**近似语义覆盖 → 仍会系统性假红。
  **判例（2026-09-10）**：`audit_skill_metadata.py` 的 `_specific` 仅 8 个字面词 →
  `qdr-meta-governance-review` 盲区段含「**已知盲区**」+具体边界（入口级审视／不产出计划／不执行修复）
  却被判「模板占位」=假红（**反模式 #63 用字面词判语义覆盖**）。修法=补 9 个**等价表述**。
- **盲区③·结构/顺序假设是一种隐性判据**：检测器对输入**结构**的假设（排序方向／字段形态）不对齐真实数据时
  会**系统性**误判，且表现为「报出很多看似合理的缺口」而非崩溃——**最难发现的一类**。
  **判例（2026-09-10）**：`audit_skill_metadata.py` 用 `records[-1]`（最后一行）当「最新」，
  而多技能迭代表为**最新在前**排序 → 取到**最老**版本 → 报「version ≠ 迭代记录最新」假红
  （6 项缺口里 3 项由此产生）。修法=改按**版本号 max** 判定·**与行序无关**。
- **自审方式**：①分诊结论**落地后必须复跑检测器**验证「报警是否消失」——不可只改数据不复查判据
  ②连续多轮同类报警未收敛 → 回查**判据本身**而非继续修数据（反模式 #44）
  ③报告「全绿」前先**交叉验证检查器自身**（2026-09-10 实证：6 项缺口里 4 项为检查器假红）。

## 🛑 自同步约束（修改本技能后强制执行）

> 来源：PTN-50 技能自同步标准（P4-2·2026-07-06 叶层扩展）。
> 本技能声明 `agent_created: true`（AI 自创建）→ 必须带本约束段，否则自动沉淀会污染技能。
> 改了本技能 → 必须逐项自查，否则文本规则不可信。

| 修改了什么 | 必须检查 | 检查方法 |
|:--|:--|:--|
| **内容/流程** | frontmatter `description` 是否仍准确反映当前能力？ | 重读 description，对比触发词覆盖与依赖引用是否仍匹配 |
| **触发词** | 是否新增/删除任务类型？路由是否覆盖？无冲突？ | 跑 `python scripts/sync_skill_registry.py --check`（含 TRIGGER_SELF_DUP / TRIGGER_CROSS_CONFLICT） |
| **版本号** | 内容/流程变更 → 必须 bump version；description 版本号须与 frontmatter `version` 一致 | 主版本+1=能力新增，次版本+1=描述/路由调整 |
| **@引用** | depends 中引用的技能/脚本仍匹配？ | 读被引用技能的触发词表与脚本存在性 |
| **references/** | 引用文件变更 → 本技能是否需同步？ | 检查 references/ 下被引内容是否已过时 |
| **cross-ref 消费方** | 谁消费本技能？ | `grep -rn "<本技能名>" ~/.workbuddy/skills/*/SKILL.md` |
| **跨宿主** | 若在 cross_host_skills.json 注册 → 改后须分发 | `python ~/.workbuddy/skills/skill-sync/references/skill_sync.py --execute` |
