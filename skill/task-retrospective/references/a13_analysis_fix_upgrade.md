# Step A1-A3：分析→修复→升级规则（对话复盘核心）

### Step A1: 分析缺陷
- 用户多费了几轮口舌？几个 bug 分了几个来回？
- 有没有同类位置没检查？（"只改一个"反模式 → 铁律 B）
- 有没有脚本不同步？（修了 A.py 但 B.py 有同款 bug）
- 有没有夸大/捏造数据？（无依据的量化 → 不算数）
- **同时列出正向产出**，禁止只列失败

### Step A1.5: 规则可执行性审计（新增）
- 对本次涉及的所有相关铁律/规则，逐一检查：
  1. 是否有**检查机制**？（grep、assert、read-back、校验脚本等）
  2. 是否有**阻断机制**？（不通过则停止，不是"建议/提醒"）
  3. 是否把"应该"写成了"必须"且带后果？
- 输出《规则可执行性清单》：
  | 规则 | 检查机制 | 阻断机制 | 是否可信 |
- **不可信的规则必须在本次复盘中修复或降级**（改为阻断、补充检查工具，或删除）

### Step A1.6: 跨维度审计（新增）
每次复盘必须从以下维度确认范围：
| 维度 | 检查问题 | 输出 |
|:--|:--|:--|
| 本项目 | 当前项目脚本/技能/规则是否都修正了？ | 已修 / 未修清单 |
| 跨项目 | 其他项目是否有同类缺陷？ | 搜索其他项目 memory（检索**本机配置目录**之记忆（🅑 `Glob <配置目录>/mem`）ory/ 或 <工作空间根>/*/） |
| 跨对话 | 历史会话是否重复出现同类问题？ | 调用 conversation_search 验证 |
| 通用 vs 项目特定 | 问题是通用模式还是本项目特有？ | 决定写入用户 MEMORY.md 还是项目 MEMORY.md |
| 🆕 跨空间 | 本次发现是否涉及 Q博士 与业务空间的 Harvest/Distribute/Consistency？ | 检查动态资产方案 §十五 + 系统架构 §十四 |
| 🆕 同源项目 | 本次问题是否源自某类可复用的架构/流水线反模式（同源指纹）？列出所有共享该反模式的空间 | 识别同源集群：grep `drq/meta_patterns/homologous_project_risk_transmission.json` + 搜 `<工作空间根>/*` 看板/数据生成脚本 |
| 前置条件 | 本次复盘依赖的数据/权限/时间范围是否满足？ | 满足 / 缺失清单 |

### Step A2: 修复技能/脚本
- 根据缺陷更新对应 SKILL.md
- 如果涉及脚本 → 同时修改 Python 脚本
- 🛑 修完 SKILL.md 必须检查：脚本是否也改了？

### Step A3: 升级规则
- 新问题模式写入项目 MEMORY.md
- 跨项目问题写入用户 MEMORY.md 铁律
- 规则必须可执行："满足 X→做 Y"，不是"以后注意"
- 区分层级：格式规范（居中/时间/单位）→ 技能级；口径统一/版本一致/数据合并 → 用户铁律

### Step A3.5: 🆕 提取可复用模式（每次复盘必备常规动作·2026-07-02 确立）

> ⚠️ **来源（2026-07-02）**：IPC日报全量升级中提炼出5个跨项目可复用模式（信源解耦/语言净化/群消息迭代/CLI路径/编码验证），用户要求每次复盘必须主动提取。

**触发条件**：任何执行模式（对话/数据/全量）复盘完成后必须执行此步骤。

**提取方法**：
1. 回看本次任务中解决的所有问题，识别出**非行业特定的通用模式**
2. 按以下分类模板逐一检查：

| 分类 | 模式示例 | 识别标志 |
|:--|:--|:--|
| **配置外置化** | Prompt信源解耦 | 修改配置需要改prompt → 抽出为JSON/技能 |
| **产出质量** | 报告语言净化 | 产出物中出现AI指令/元注释 → 建立违禁词+自检 |
| **格式收敛** | 群消息模板迭代 | 同一格式反复调整≥3次 → 锁定固定模板+收敛原则 |
| **环境兼容** | CLI路径标准化 | 脚本在不同环境表现不一致 → 统一调用路径 |
| **数据完整性** | 编码防乱码 | 中文内容偶发损坏 → Write+Read双Verification |
| **流程固化** | 任何≥2次重复执行的步骤 | 手动步骤反复做 → 写入技能/自动化prompt |

3. 每条模式标注：
   - **问题**：做了什么事暴露了这个问题？
   - **解决方案**：具体怎么修的？
   - **适用场景**：其他什么项目/任务能用到？
   - **存放位置**：`~/.workbuddy/MEMORY.md` 可复用模式库

4. **如果提取出 ≥1 个新模式 → 必须写入用户 MEMORY.md「🔄 可复用模式库」**
5. 如果本次无新模式 → 输出"本次无新增可复用模式"，但仍需执行检查（在复盘报告中一行即可）

**输出格式**：
```
🔄 可复用模式提取：本次提取 X 个新模式
- 模式N：名称 → 已写入 ~/.workbuddy/MEMORY.md
- 无新增 → 跳过
```

### 🆕 Step A3.6a：E0-1 机制自审（meta-RSI 触发·R1-1 管道·2026-08-30）

### 🆕 Step A3.7：对话复盘→任务自动提案（2026-08-06·Phase B·九维审计确立）

> **来源**：2026-08-06 九维全链路审计发现——复盘报告的"具体可执行任务"（非META模式·非全局修订）没有进入 §一 的路径。AI 对话复盘产出是 11 类复盘产出中频率最高但唯一无自动化管线的类型。

**触发条件**：任何执行模式复盘完成后（对话/全量/深度），AI 必须执行此步骤。

**强制步骤**：
1. 复盘报告生成后，AI 从复盘报告中提取「具体可执行任务」：
   - 脚本修复类："修复 `scripts/XX.py` 的 YY 问题"
   - 配置更新类："更新 `governance/data/YY.json` 的 ZZ 配置"
   - 清理/归档类："清理 `Backups/` 下 N 个过期文件"
   - 管线修复类："对接 AA → BB 的管道断点"
2. 对每个可执行任务，通过 `task_factory.create_task()` 创建标准 §一 任务行：
   ```python
   from task_factory import create_task, insert_task_to_plan
   from task_dedup import check_duplicate, build_existing_hashes
   ```
3. 内容去重：`check_duplicate(desc, existing_hashes)` → 命中匹配任务时**须四层核验该任务是否真正完成**（唯一真相源见 `infrastructure-audit` 技能「Step 0 查任务主表（四层核验）」：L1标题→L2状态→L3痕迹→L4效果）。L2-L4 任一不符=任务「执行不彻底」→**补修复任务而非跳过**（反模式#43/#44）；仅 L1-L4 全通过才「跳过已存在任务」。
4. 写入 §一：`insert_task_to_plan(task_line)`
5. 在复盘报告末尾输出："📋 已自动提案 N 个任务→§一（跳过 M 个重复）"

**判定规则**：
- 是「具体可执行」→ 创建 §一 任务
- 是「元模式/系统性规则」→ 走 Function B（META 管道），不重复创建
- 是「观察/建议」→ 留在复盘报告中，不创建任务

**禁止行为**：
- ❌ 复盘完成后不提取可执行任务
- ❌ 把元模式类发现当成具体任务创建（导致 Function A/B 重复）
- ❌ 不运行去重检查就创建任务
