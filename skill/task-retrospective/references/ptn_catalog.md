### 🆕 可复用模式 PTN-34：精简安全评估框架（2026-07-04 提取·经 3 轮修正完善·v2.0 泛化版）

> **v1.0→v2.0 泛化（2026-07-04 19:39）**：本模式最初仅覆盖自动化 prompt 瘦身。经用户要求"所有类型的精简约简都应有判断标准"，现已泛化为适用于技能、脚本、自动化、文本、记忆、规则等全部内容类型的通用框架。

#### PTN-34.1 适用范围

本框架适用于以下任何类型的内容精简：

| 类型 | 示例 | 特殊风险 |
|:--|:--|:--|
| **自动化 prompt** | IPC日报、周度复盘、跨窗口同步 | 授权检查、依赖声明、异常路径容易遗漏 |
| **技能 SKILL.md** | task-router、task-retrospective | 触发词、下游建议、禁止行为不可删 |
| **Python 脚本** | preflight_check.py、coherence_check.py | 函数签名、import 依赖、异常处理不可删 |
| **记忆文件 MEMORY.md** | 项目 MEMORY.md、全局铁律 | 规则编号、文件路径、触发条件不可删 |
| **规则/铁律** | 🛑 铁律、自检项、方法选择矩阵 | 阻断条件、例外条款不可删 |
| **文本/指南** | 复盘指南、本质定位 | 章节锚点、交叉引用编号不可删 |

#### PTN-34.2 五步安全瘦身法（通用版）

```
Step 1: 提取旧版功能点清单
  逐段读原文，每条标注：功能描述 + 为什么需要 + 删掉后果

Step 2: 对比映射
  在新版中逐条定位 → 标记 ✅ 已覆盖 / ❌ 缺失 / ⚠️ 隐含但不明确

Step 3: 补回 ❌ 和 ⚠️
  ❌ → 必须补回；⚠️ → 要么补回，要么在新版中明确声明"由XX技能/文件承担"

Step 4: 消费者扫描（🆕 v2.0 新增）
  grep -rn "关键词" 扫描所有消费方（其他技能/自动化/MEMORY.md/app-config.json）
  确认无断裂引用

Step 5: 验收断言
  运行测试（如有）+ 逐项确认清单全绿 → 方可标记完成
```

#### PTN-34.3 五类"绝对不能删"（通用版·按类型）

| 类别 | 自动化 prompt | 技能 SKILL.md | 脚本 | 记忆/规则 | 文本/指南 |
|:--|:--|:--|:--|:--|:--|
| **执行前置** | "不依赖历史消息" | 触发词列表 | import 语句 | 🛑 铁律编号 | 交叉引用锚点 |
| **依赖声明** | 授权检查 | imports/paths 表 | sys.path.insert | 文件路径 | 版本依赖 |
| **异常路径** | 超时处理 | 禁止行为 | try-except | 例外条款 | 边界条件 |
| **安全边界** | 幂等性要求 | 环境/权限声明 | 文件写入前备份 | 阻断规则 | 警告/提示 |

#### PTN-34.4 三问三答判断法（快速自测表）

| 可以删 | 不可以删 |
|:--|:--|
| Q1: 删掉后，AI 还会做这件事吗？ → **会** → 可以删 | Q1: 删掉后，AI 还会做这件事吗？ → **不确定** → 不能删 |
| Q2: 这个信息在其他地方已经定义了？ → **是，且 AI 一定会读到** → 可以删 | Q2: 这个信息在其他地方定义了？ → **是，但 AI 可能读不到** → 不能删 |
| Q3: 这是解释性的废话？ → **是** → 可以删 | Q3: 这是触发/阻断/异常的边界条件？ → **是** → 不能删 |

#### PTN-34.5 验收断言清单（写入前逐项打勾）

- [ ] 旧版每个功能点在新版中有对应（Step 2 全绿）
- [ ] 所有 ❌ 项已补回或标注"有意删除 + 原因"
- [ ] 消费者扫描完成：grep 了所有引用方，无断裂
- [ ] 未引入新的歧义
- [ ] 如果有测试 → 测试通过
- [ ] 🆕 如果是 Q博士 产出 → 已按 §六·全局复用路由 写入全局位置

### 🆕 可复用模式 PTN-35：动态发现 vs 静态名单（2026-07-04·Q博士 核心方法论·全空间验证版）

> **来源**：全局同步时遗漏指南文档的版本同步，因为依赖表没列出这类消费方。深挖后基于全空间 246 JSON + 234 PY + 190 MD 的真实分布，建立了覆盖 15 种产出物形态 × 5 种空间类型的动态检索矩阵。

#### PTN-35.1 核心洞见

```
静态名单 = 只能列出"你想到的" → 迟早有遗漏
动态检索 = grep/Glob 全项目 → 不会遗漏
```

#### PTN-35.2 三步法（通用·可落地）

```
Step 1: 定义检索域（按空间类型）
  报告密集空间：MD + JSON + PS1 + config
  数据仓库：JSON + PY + SQL
  通用规则空间：MD + PY + JSON

Step 2: 执行批量检索
  Glob 对应文件的元数据（size+modified+mtime）
  grep 搜索关键词

Step 3: 比对版本/一致性
  消费方文件 vs 源文件 → 版本号一致？
  章节引用 vs 实际章节 → 锚点存在？
```

#### PTN-35.3 应用场景矩阵（基于全空间真实文件类型）

| 场景 | 静态名单 → 会遗漏 | 动态检索 → 发现全部 |
|:--|:--|:--|
| 复盘指南版本升级 | 只更新了引用表里的消费方 | grep 出"版本 vX·更新 2026-07"发现新引用方 |
| FILE MANIFEST 版本同步 | 只查了直接依赖表 | grep 出所有引用了该版本号的文件 |
| 跨空间架构变更 | 只更新了已知的关联文件 | grep 出隐藏的引用方（如自动化 prompt 中硬编码的路径） |

#### PTN-35.4 空间类型 × 检索策略

| 空间类型 | 文件特征 | 检索策略 |
|:--|:--|:--|
| 报告密集(如海事/工控机) | MD为主+JSON+PS1 | Glob *.md → grep 关键词 |
| 数据仓库(如 Data-全局) | JSON+PY+SQL | Glob *.json *.py → grep |
| 通用规则(如 Q博士) | MD+PY+多种格式 | Glob 全量 → grep 关键词 |

#### PTN-35.5 与已有 M 编号的互操作

- PTN-35 提供检索方法论（如何找）
- PTN-34 提供安全精简框架（找到后如何评估精简）
- 两者在"消费者扫描"步骤中交汇

### 🆕 可复用模式 PTN-36：多轮重复任务识别与消除（2026-07-04·积分日志深度复盘）

#### PTN-36.1 识别信号

| 信号 | 检查方法 |
|:--|:--|
| 同一任务重复出现 > 2 次 | 检查该空间的历史 `复盘报告` + `MEMORY.md` 中的待办清单 |
| 修复方案含有明确的"上上次也修过" | 检查 `MEMORY.md` 的待办完成记录 |
| 用户明确说"上次不是修过了吗" | 直接记录 |

#### PTN-36.2 根因分类与消除策略

| 根因类型 | 特征 | 消除策略 |
|:--|:--|:--|
| **漏写规则** | 修复了但没写规则 → 下次遇到又修一次 | 写规则（🛑 铁律·安全规则） |
| **规则定位错误** | 规则写在了错的地方（如写在项目 MEMORY 但需要全局铁律） | 定位到正确位置 + 删除旧位 |
| **触发词缺失** | AI 做对了但用户不知道怎么调用 | 注册触发词到 router + 更新技能 |
| **执行遗漏** | 规则写了但复盘时没执行 | 将规则纳入自动化或 A4.x 检查步骤 |

#### PTN-36.3 验收标准

- 同类错误 30 天内不重复出现
- 待办闭环率 ≥ 90%

#### PTN-36.4 经济效益

- 识别-消除一次 ≈ 省 2-5 次重复修复（~60分钟 × 2-5 = ~120-300分钟/次）
- 需投入：分析+写规则+自动化（~30分钟）
- ROI ≈ 4x-10x

### 🆕 可复用模式 PTN-38：技能重构安全框架（2026-07-04·本次重构自身经验提取·META-25自反身性应用）

#### PTN-38.1 六步安全重构法

```
Step 1: 识别重构动机
  用户在同一个任务中反复修改同一技能？→ 重构信号

Step 2: 功能点清单
  逐段读原 SKILL.md，每条标注：功能描述 + 为什么需要

Step 3: 设计新结构
  按功能模块分组 → 设计新的技能结构大纲

Step 4: 新旧映射
  新结构中的每个模块→来源旧功能点 → 标记 ✅/❌/⚠️

Step 5: 消费者扫描
  grep 所有引用了本技能的文件 → 更新引用路径/名称

Step 6: 验收
  Step 2 全绿 + 消费者扫描全绿
```

#### PTN-38.2 核心原则

```
1. 旧版功能点 100% 映射到新版（零遗漏）
2. 消费者扫描无断裂（零遗漏）
3. 重构前后触发词兼容（旧触发词仍有效）
```

#### PTN-38.3 适用场景

- 技能从单层结构改为分层结构
- 技能拆分为多个子技能
- 技能合并

### 🆕 可复用模式 PTN-37：单次综合分析替代串行多轮（2026-07-04·自反身性应用）

#### PTN-37.1 问题

旧版 B1-B8 需要 8-10 次串行 Python 调用（~140 分钟）。用户说"效率太低了，能不能一次搞定？"

#### PTN-37.2 解决方案

```
1. 分析旧版 B1-B8 之间的数据依赖关系
2. 识别可以并行的维度（独立数据源）
3. 设计递归口径表 + 单次模板
4. 将依赖项整合为递归脚本

核心公式：
  串行轮数 = 独立维度数 - 数据依赖数
  理想轮数 = 1（所有维度可并行）
```

#### PTN-37.3 落地

- 设计"单次递归口径表"定义
- 按口径表生成单次对应脚本
- 脚本内部做数据隔离（不要维度间污染）

#### PTN-37.4 推广

适用于以下场景：
- 多维度数据源分析
- 跨系统数据聚合
- 报告生成（多模块并行）

### 🆕 可复用模式 PTN-46：建造树模型——超级智能体的生长理论（2026-07-05·溯源复盘）

> **来源**：Q博士 跨空间三通道同步深度溯源。核心发现：超级智能体的成长不是线性的，而是树状的——根→干→枝→叶，每层依赖下层的完整。

#### PTN-46.1 四层结构

| 层 | 含义 | 生长顺序 | 建造顺序建议 |
|:--|:--|:--|:--|
| **根·宪章** | 不可变的概念基础 | 第1阶段 | 本质定位、进化回路、边界约束 |
| **干·方法体系** | 持续生长的核心能力 | 第2阶段 | 复盘模板、技能生态、规则引擎、记忆系统 |
| **枝·跨空间服务** | 向外的触达能力 | 第3阶段（必须等树干完整） | Harvest/Distribute/Consistency |
| **叶·自动化巡检** | 日常自我维护 | 第4阶段（最后） | 每日巡检、周日维护、健康报告 |

#### PTN-46.2 建造原则

1. **干不生则枝不伸**：方法和技能体系不完整，跨空间服务不可能可靠
2. **叶不落则干不显**：没有被自动化取代的人工维护，不是真正的自动化
3. **根不动则树不倒**：宪章变了，整个系统需要重新生长
4. **每层依赖下一层**：枝的伸展需要干的强壮，干的粗壮需要根的稳固

#### PTN-46.3 适用于什么场景

- 新建超级智能体时，作为建造路线图
- 系统完成重大跃迁后，用来定位在建造树中的位置
- 溯源复盘时，作为分析框架

#### PTN-46.4 落地

- `docs/跨项目全量复盘指南.md` 模板H §七（建造树模型·v4.1）
- task-retrospective → 本条目
- 本质定位 → §1.4 建造树模型
- `docs/复盘体系演化史.md`（版本历史+建造树完整记录）
- 流程日记 → 阶段12·建造法
