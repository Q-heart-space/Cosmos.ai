```
🔍 关联扫描：本次修改 [X] → 检查 [同类文件/标题/TOC/构建脚本/Y项] → [已同步N处 / 无关联项]
```

### 🆕 Step A5.5: 语义层消费方清单（强制·2026-07-12·L1.5语义层接入）

> **定位**：M.A.R.L 闭环的 Link 端自动化——Recall 之后不再手工猜测"哪些文件要同步"，而是通过语义层推理自动生成消费方清单。
> **依赖**：`scripts/cross_world_translator.py` v1.0 + `scripts/ontology_manager.py` v1.0

**触发时机**：任何 🏛️ 级文件变更后、Step A5 关联扫描之后。

**执行步骤**：
1. 识别本次变更涉及的核心概念（从复盘报告的「变更摘要」提取）
2. 对每个概念运行 `cross_world_translator.py --concept "概念名"`
3. 收集所有产品化影响 → 逐项检查目标文件是否需要同步
4. 输出「消费方清单」格式：
```
🆕 语义层消费方清单：
  概念 [X] 变更 → 以下文件/字段可能需要同步：
  - [文件A] §[章节]: [检查项]
  - [文件B] §[章节]: [检查项]
  ...
  建议：按清单逐项确认，P0 项必须同步。
```

**阻断规则**：概念变更触发 P0 翻译规则（TR-001/TR-006）且未执行消费方清单 → 🛑 禁止标记复盘完成。

## 🆕 🆕 Step A6：溯源复盘·灰度同步闭环（模板H配套·v3.19·2026-07-05 确立）

> **来源**：跨空间三通道同步深度溯源复盘。复盘输出报告后，用户明确要求"复盘完了，哪些需要同步修改的？复盘不是结束，只是新一轮迭代的开始"。建立了"溯源复盘→灰度同步计划→人类确认→依次执行→逐项验证→全链路闭环"的标准流程。

### 触发时机
模板H（溯源复盘）和模板G（强制深度复盘）完成后，在 Step A4 闭环确认之前。

### 强制步骤

| 步 | 名称 | 做什么 | 验收 |
|:--|:--|:--|:--|
| **S1·提取** | 从溯源报告中提取所有需要同步的交付物 | 按 P0/P1/P2 分级，列出文件路径+要改什么+依据 | 清单≥5项 |
| **S2·确认** | 向人类输出「灰度同步计划」 | 逐项说明优先级和理由，等待确认 | 人类回应"执行" |
| **S3·依次执行** | 按优先级从高到低修改每个文件 | P0→P1→P2，每项完成后验证 | 每项标注✅ |
| **S4·全局同步** | 全部修改完成后运行 `asset_repair.py --auto-sync` | 版本升级+注册表刷新+健康检查 | DIRTY_ROOT=0 |
| **S5·交叉验证** | V1-V5 全量验证 | 残留/消费方/版本/运行时/自查 | 全通过 |

### P0 硬约束（不执行则阻断）

- 复盘指南 → 必须同步（模板新增/维度新增/编号增删）
- task-retrospective 技能 → 必须同步（新模式/新可复用模式）
- 流程日记 → 必须同步（阶段追加）

### 输出格式

```
🔄 灰度同步计划（A6）：
  P0: 复盘指南[模板H+§八·A+§九] + task-retrospective[A6+PTN-46] + 流程日记[阶段12]
  P1: 本质定位[建造树] + 综合规划[§附录·AC(快照)] + 成长记录[里程碑] + MEMORY[建造树]
  P2: preflight[待建检测] + asset_repair[溯源复查]
→ 用户确认：{等待}
→ 执行完成：X/X 项 ✅
→ 全局同步：asset_repair.py --auto-sync ✅
```

### 禁止行为
- ❌ 溯源复盘完成后不输出灰度同步计划
- ❌ 灰度同步计划跳过 P0 项
- ❌ 修改后不验证、不全局同步
