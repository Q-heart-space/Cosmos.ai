# 宿主运行时性能归因（host-runtime-triage）

## 🚧 能力边界（先读这段，避免误用）

本技能与相邻技能**职责正交**，不可互相替代：

| 技能 | 回答的问题 | 对象 | 典型触发 |
|:--|:--|:--|:--|
| **本技能** | **「为什么整机都慢」** | 宿主运行时 / OS 资源 | 卡顿·命令变慢·进程启动慢 |
| `detector-signal-triage` | 「这条报警本身可信吗」 | **治理检测器**输出的值 | 检测器红灯·0分·孤立项 |
| `qdr-full-chain-audit` | 「批量脚本跑得慢怎么校准」 | **脚本执行性能** | 检查器批量超时·单维快验 |

**判定口诀**：
- 慢的是**整个系统**（连 `ls`、内建循环都慢）→ **本技能**
- 慢的是**某个检测器的结论不可信** → `detector-signal-triage`
- 慢的是**一批治理脚本里的某几个** → `qdr-full-chain-audit`

⚠️ **本技能不处理**：检测器结论真伪（归 `detector-signal-triage`）、脚本内部超时预算校准（归 `qdr-full-chain-audit`）。

## 何时使用（务必先跑探针确认是「整机慢」）

- 宿主报 `operation blocked by hook: Hook timed out`
- **脚本日志显示"1 秒完成"，宿主却报超时**（典型的归因错位信号）
- 命令/工具调用**普遍**变慢、`ls` 要几秒、程序启动要几秒
- 怀疑"某个组件有问题"但换了几个组件都没修好

> **若只有单个组件慢、整机不慢** ⇒ 不属于本技能，应回到该组件内部审计。

## 核心原则

> **归因必须落在可测量的物理量上（耗时 / CPU 秒 / 进程数），
> 绝不能落在"看起来合理的名词"上（杀软 / 代理 / 句柄 / 缓存）。**

名词类归因几乎总能自圆其说，因此**几乎总是错的**，且会让人反复修错地方。

## 第一步：三层零依赖探针（一次跑完，60 秒内出结果）

```bash
# ① 纯内建循环——不创建进程、不读磁盘、不联网
for n in 1 2 3; do s=$(date +%s%N); i=0; while [ $i -lt 10000 ]; do i=$((i+1)); done; e=$(date +%s%N); echo "$(( (e-s)/1000000 )) ms"; done

# ② 单目录 ls——只测 I/O + 进程创建
for n in 1 2 3; do s=$(date +%s%N); ls . >/dev/null 2>&1; e=$(date +%s%N); echo "$(( (e-s)/1000000 )) ms"; done

# ③ 解释器冷启动——测 spawn 全链路
for n in 1 2 3; do s=$(date +%s%N); python3 -c "pass"; e=$(date +%s%N); echo "$(( (e-s)/1000000 )) ms"; done
```

**正常基线**：① ~50ms · ② ~50ms · ③ ~50–300ms

### 判据表（关键）

| ① 内建循环 | ② ③ | 结论 | 处置 |
|:--|:--|:--|:--|
| **慢**（>500ms） | 慢 | **CPU 被抢占** —— 与杀软/磁盘/网络**无关** | 查 CPU 大户，错峰/关停抢占者 |
| 正常 | **慢** | I/O 或杀软实时扫描 / spawn 路径问题 | 查杀软、磁盘、PATH 解析层 |
| 正常 | 正常 | 问题在被测组件自身 | 回到组件内部审计 |

> **① 是最有价值的一根探针**：它**零外部依赖**。
> **① 若也慢，就不可能是 I/O、杀软、或任何外部程序的锅——只能是 CPU 被抢。**

## 第二步：定位抢占者（CPU 归属）

```bash
# 进程数量突增检测
tasklist /FO CSV | grep -ci python

# CPU 累计归属（累计 CPU 秒，非瞬时占用率）
powershell -c "Get-Process | Sort-Object CPU -Descending | Select-Object -First 15 Name,Id,CPU,@{n='rssMB';e={[int]($_.WorkingSet64/1MB)}} | Format-Table"
```

**要点**：
- 按 **累计 CPU 秒** 排序找大户（`CPU` 属性），而非瞬时占用
- 对比**同类宿主的相对倍率**（如 DSH 7095s vs WorkBuddy 3739s = 1.9 倍）比绝对数字更有意义
- 统计**子进程数量级**（如 81 个 python、3GB 内存）——编排链自繁殖是常见形态

---

## 第三步：阻断因果验证（决定性实验）

**假设 → 消除变量 → 复测 → 因果确证**

1. 声明假设："X 是主因"
2. **消除 X**（关停/暂停/隔离），其他条件不变
3. **用完全相同的测量方法复测**
4. 看改善幅度：
   - **改善 >80%** → 因果确证，收工
   - **改善有限** → 假设推翻，回到第一步找第二消耗源

**判例（2026-09-11）**：
```
现象：UserPromptSubmit hook 报 30s 超时，但脚本日志显示 1 秒完成
误判史：脚本慢(X) → 绝对路径(X) → 杀软(X) —— 全部被实测推翻
正解：纯 bash 循环慢 195 倍（零依赖）⇒ CPU 被抢 ⇒ 关停 DSH
结果：bash 循环 9760ms→727ms（↓87%）· python 启动 5520ms→690ms（↓88%）
      python 进程 81→1 · hook 端到端 30s(超时)→700ms
```

## 第四步：归因错位自查（高频陷阱）

**症状：日志说 A 很快，宿主说 A 超时。**
→ **几乎总是：超时的那次和记录成功的那次不是同一次运行。**

```
第 1 次（超时）：宿主 spawn 阶段就 >30s → kill
              ⇒ 被测脚本【压根没启动】⇒ 日志无任何痕迹
第 2 次（重试）：成功 ⇒ 日志记下"1 秒完成" ← 大家只看这一条
```

**防呆**：遇到"日志与报错矛盾"，**先确认记录的是不是同一次运行**，再怀疑代码。

## 测量纪律

| 纪律 | 说明 |
|:--|:--|
| **多次采样 + 中位数** | 噪声可达 ±3s，单一慢值不可作结论 |
| **测量方法保持一致** | 改前改后必须同法同参，否则不可比 |
| **先立基线再动手** | 没有基线就无法判断改善 |
| **对照基线要可信** | "正常应 ~50ms" 之类的理论值需标明来源，机器基线可能本就偏离 |

## 反模式

- ❌ 拿"看起来合理的名词"当结论（杀软/代理/句柄/缓存）
- ❌ 只跑一次就下结论
- ❌ 改完不测就宣布修复
- ❌ 用组件日志的成功记录解释另一次运行的失败
- ❌ 未先确证因果就动配置（配置改动应在根因确证后、作为验证手段而非猜测手段）

## 修复优先级通则

| 级别 | 动作 | 说明 |
|:--|:--|:--|
| **治本** | 消除资源抢占（错峰 / 关停大户） | 唯一真正解法 |
| **安全垫** | 放宽超时配额 | 不治根，但消除"被 block 需重发" |
| **卫生** | 路径/配置优化 | 实测 <1% 收益的不值得做 |

> **若无法消除抢占源**：至少放宽配额保住可用性，并如实说明"这是安全垫不是修复"。

## 盲区与自审

> v1.2（2026-09-12·元模式复盘驱动·反模式#45）

- **①探针读数受宿主噪声污染**：归因依赖 CPU/IO/基线三类读数，若宿主同时在跑重任务（如全量资产扫描），读数会被污染 → 须两次采样对照，单次读数不下结论。
- **②零依赖探针不等于全谱诊断**：本技能只回答「是不是宿主整体变慢」与「主因是 CPU/I-O/基线哪一类」；不替代业务级性能剖析（脚本内部热点、锁竞争）。
- **③「命令普遍变慢」可能是假象**：单命令慢易被泛化为「宿主卡顿」→ 判据须以多命令对照 + 基线对照为准，避免单点异常归因到宿主。
- **自审触发**：归因结论给出后，抽 1 条命令重复测验证可复现性；两次结论不一致 → 先怀疑探针/宿主噪声。

### 真实判例（本技能何时会给过错误/不完整结论）

- **判例1（2026-09-11·WorkBuddy 5.5.6 命令级进程组回收）**：现象是 detached runner 被秒杀、心跳停摆，**初判误判为「脚本自身崩溃」**。本技能的贡献：同调用内 t+6s 探针仍 ALIVE、调用返回即 DEAD ⇒ 判定为**宿主命令级回收**，**失效**的是「跨调用存活」这一前提而非脚本。教训：同一探针必须在「调用内」与「调用后」两次采样，否则会把宿主侧回收**误判**为脚本缺陷。
- **判例2（2026-09-12·hook 超时被误判为性能问题）**：`pre_write_hook` 报超时 18–30s，直觉归因「脚本太慢」——实测业务逻辑远小于超时值 ⇒ 真因是**有界性缺失**（无界 stdin / 单次超时==宿主配额），**不是**性能。本技能的**边界**：不回答脚本内部热点/锁竞争；遇「实测远小于超时却报超时」须优先怀疑有界性与宿主配额。
- **漏检场景**：宿主噪声（并发重任务）会污染单次读数 → **本技能的漏检风险**是把噪声当主因；故结论须两次采样对照，不一致时不下结论。
