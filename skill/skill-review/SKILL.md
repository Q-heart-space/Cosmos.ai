# skill-review：技能审阅（标准化 7 阶段 + 前置边界判定）

> **定位**：把"审阅一个业务技能包"标准化（源自三样本元模式，见 references/examples/）。**只审不改**：输出问题清单+修复方案+验收单，修复由用户执行。
> **纪律**：先实测后审阅；边界先行；双视角并行；能力必落任务；计数复核；双文件锚点核对。Step 0=阶段-2/-1（取证+归因）；Step 1-7=阶段 1-7。
> **changelog**：v1.3.0（2026-09-16 审2 增运行视角四问 + 好技能 8 条标准——①整体框架可识别②核心重点可识别③触发词→执行范围映射④详细步骤可查·配套 references/good-skill-criteria.md + skill-file-spec.md 定标）；v1.2.0（2026-09-11 D4 元数据维补 `triggers` 四查——存在性/自身重复/跨技能冲突/过宽词·对齐 sync --check v1.21 新增 TRIGGER_SELF_DUP+TRIGGER_CROSS_CONFLICT 与 task-router 分流表 v3.29；触发词是功能性元数据，决定技能能否被正确路由，原 D4 仅查 version/changelog/description 属覆盖缺口）；v1.1.1（2026-09-08 审2 增 D8 自进化机制审查——盲区段真实/迭代留痕/结构分层/机制词 4 判据·STAGNANT→P1·对齐 skill_self_evolution_check/术语表 #345·技能质量审阅含"技能是否在进化"维）；v1.1.0（2026-09-06 G6 供应链风险五查——SkillSpector 外部借鉴落地·审1 增维·详见 dimensions.md）；v1.0.1（2026-09-04 补两层坐标系防混用声明·description/引言行压缩）；v1.0.0（创建·三样本元模式；递归自审补 version/锚点/降级条款）。


## 使用流程（按序执行，每步有产出）

### Step 0 · 现象与入口判定（前置 · 最重要）
> **坐标系声明（防混用）**：本技能用**归因坐标系 A/B/C/D**（问题产生层）；**协议坐标系 Q1-Q4**（交互策略）属入口/路由层、不归本技能——两层不可混用（详表 dimensions.md 前置节）。
1. 记录用户原始现象（报错/查不到/答错/不适用），**不预判**。
2. 最小复现 + 取证：真跑一次技能主路径（触发/查询/输出），采集证据 E1..En。
3. **边界归因**（判定是否技能问题，还是系统/数据/使用问题——归因坐标系 A/B/C/D）：
   - 判定维度 = 问题产生层：**A 技能本体 / B 系统环境 / C 数据内容 / D 使用方式**
   - 归因证据：换入口/换宿主仍复现→A；API 状态码/凭据/网络→B；命中但内容错/术语不统一→C；操作与设计不符/"都不是"→D
   - 交叉裁定：同现象多因（如 400=系统参数上限×技能体积）→ 各因分层登记、各修各的
4. **边界声明**：A 象限有可修项才进 Step 1；仅 B/C/D 按层给修复。报告首行写"审阅边界=A；B/C/D 另行处理"。
   - ⚠️ 反模式：Q1-Q4 判归属 / A/B/C/D 选策略 = 坐标系混用；系统问题当技能修 = 修错对象；技能问题当环境甩锅 = 掩盖缺陷。

### Step 1 · 双视角审阅（并行双审）
- **审1 治理/运行视角**（对抗式）：合规/脱敏/降级协议/不可逆操作/依赖声明/**供应链风险（G6·含 scripts 捆绑二进制/远程拉取即执行/安装钩子）**/体积是否触发平台限制。
- **审2 本体质量视角**：结构/元数据(version·changelog·description)/自反身性(声明=实现)/资产一致性(唯一源·副本漂移·递归打包)/指令可执行性/**🆕 运行视角（2026-09-16·AI 运行四问）**：①**整体框架可识别**——AI 读 SKILL.md 后 30 秒内能否知道「模式/步骤/环节全貌」（如复盘有几种模式、审计有几步）②**核心重点可识别**——阻断级/门禁/判据表（分级/路由/四分法）是否在 SKILL.md 而非仅 references ③**触发词→执行范围映射**——不同触发词能否判定「执行部分 vs 全部」（触发词表→执行模式/步骤范围）④**详细步骤可查**——references 指针清晰·按需加载不中断主流程。**（🆕 好技能 8 条标准 + 放主体/参考铁律见 `references/good-skill-criteria.md`·2026-09-16 定标）**/**自进化机制（🆕 v1.1.1·盲区段真实/迭代留痕/结构分层/机制词 4 判据·STAGNANT→P1 必改）**。
- 产出：两审问题清单（每条：问题/证据/优先级 P0-P3）。详细维度清单见 `references/dimensions.md`（审2 D8 自进化·审1 G6 供应链）。

### Step 2 · 能力映射（查存量方法论迁移）
- 盘问可用方法论/平台能力（本地治理方法 M#、跨宿主能力 X#），逐条转译为**技能内可执行规则**（不依赖源系统）。
- 出口判定：每条能力必须落到 ≥1 个任务；只当思路讨论 = 未完成。

### Step 3 · 外部权威对照（防闭门造车）
- 对照官方 skill 规范（渐进披露 W1-W8 / scripts 分工 / 祈使句 / 第三人称 description / agent_created 标记），逐条核对。
- **🆕 对外发布技能标准（G7·2026-09-15 定标）**：若技能标注 `distribute_external: yes` 或拟发布公开市场（GitHub / 技能市场），须额外核对「发布要素九项」——详见 `references/external-release-standard.md`：
  - **结构六件**：README.md / CHANGELOG.md / CONTRIBUTING.md / LICENSE / .gitignore /（.github/ 若含自动化）
  - **frontmatter 四项**：distribute_external: yes / license / 中英双语 description / 能力边界声明
  - **自闭环四项**：references 非空（若引用）/ scripts 可运行（无本机路径）/ 无 TODO 遗留 / 无本机信息泄露
  - **参考范式**：ai-drift-guard-release（首个达标样本·含 .git+.github 周一自动化）

### Step 4 · 定位校准（第一原理）
- 推导技能存在意义 FP1..FPn → 名实相符裁定（定位是否夸大/过窄，如"系统"vs"中台"）。
- 裁决项 R#：每项给默认建议 + 依据；非紧急可默认采纳避免阻塞。

### Step 5 · 方案统一（单一版本）
- 两审合并去重 → 任务全表（ID/优先级/执行人/依赖/来源）→ **计数复核**（总表=域表=逐项加和，防漂移）。
- 每任务五段式：问题 / 方向 / 方案 / 验收 / 执行人。模板见 `references/templates.md`。

### Step 6 · 交付分层（渐进披露，面向读者）
- 薄执行手册（30 秒看懂/Part A 手工/B 批次/验收单）+ 厚依据附录（为什么）。
- 出口判定：**双文件锚点逐条核对**——手册引用的附录章节必须真实存在、版本/计数两文件一致（无死引用）。

### Step 7 · 闭环验收
- 回归单 R-1..R-n（每次改动勾选），模板见 `references/templates.md`。
- 里程碑判定：P0 全绿=试点（M1）→ P1 全绿=放量（M2）→ 持续=常规维护（M3）。

## 输出物（三件套）
1. **审阅报告/任务清单**：边界声明 + 两审问题 + 任务全表（P0-P3）。
2. **执行手册**：面向执行者（同事可无 Q博士 环境照做）。
3. **依据附录**：为什么这么修（渐进披露，按需查阅）。

## 回归基准（三案例 · 每次改流程后复验）
- S1_apq-platform-content（64 行·内容真实性）｜S2_apq-marketing-copy（264 行·广告合规）｜S3_fae-knowledge-base（365 行·400 边界+双文件呼应）——examples/ 下
- 变更本技能后必须用三案例快跑（归因→审阅维度→输出形态），确认不退化。

## 维护章程（本技能自身 · 不可违反）
- 主文件 ≤120 行 / ≤6 KB（与审阅红线一致，以身作则）。
- 审阅输出前必须过边界判定（Step 0），禁止直接开审。
- 计数、版本、锚点声明必须与实际一致（防 #72 漂移）。
- 降级协议：遇 API 异常/超时/环境不可用 → 记证据 E# 转人工核验，禁止用推断替代实测（防 #43）；无法取证标注"待取证"。

## 盲区与自审（v1.1.1 补·2026-09-08·技能自进化·反模式#45）

- **盲区声明**：7 阶段审阅依赖审阅者（AI）按维度清单执行——维度清单未列的新型缺陷漏审；边界归因（A/B/C/D）依赖证据采集完整性，证据不足时可能误归因。
- **实证判例入段**：①**自进化审查缺失**（2026-09-08·用户'skill-review 有没有增加技能自进化审查'）——审 2 原无 D8 自进化维度·审阅技能不查其盲区段真实性/迭代留痕/是否 STAGNANT·技能"声明会进化"但审阅不验证 → 补 D8（4 判据·STAGNANT→P1）·审阅技能自身也须有盲区段（本段即以身作则）②**检测器口径联动**（2026-09-08）——skill_self_evolution_check 判据（盲区真实/迭代/结构/机制词）是 D8 的机器化前身·审阅前可先跑检测器取基线·人工审 D8 是对机器判据的语义复核（字面命中≠真实盲区）。
- **自进化闭环**：审阅暴露盲区/失效 → 补本段 + 维度清单 → 版本升级 → skill_self_evolution_check 验证（STATIC→EVOLVING=真进化）。

## 🛑 自同步约束（修改本技能后强制执行）

> 来源：PTN-50 技能自同步标准（P4-2·2026-07-06 叶层扩展）。
> 本技能声明 `agent_created: true`（AI 自创建）→ 必须带本约束段，否则自动沉淀会污染技能。
> 改了本技能 → 必须逐项自查，否则文本规则不可信。

| 修改了什么 | 必须检查 | 检查方法 |
|:--|:--|:--|
| **内容/流程** | frontmatter `description` 是否仍准确反映当前能力？ | 重读 description，对比触发词覆盖与依赖引用是否仍匹配 |
| **触发词** | 是否新增/删除任务类型？路由是否覆盖？无冲突？ | 跑 `python scripts/sync_skill_registry.py --check`（含 TRIGGER_SELF_DUP / TRIGGER_CROSS_CONFLICT） |
| **版本号** | 内容/流程变更 → 必须 bump version；description 版本号须与 frontmatter `version` 一致 | 主版本+1=能力新增，次版本+1=描述/路由调整 |
| **@引用** | depends 中引用的技能/脚本仍匹配？ | 读被引用技能的触发词表与脚本存在性 |
| **references/** | 引用文件变更 → 本技能是否需同步？ | 检查 references/ 下被引内容是否已过时 |
| **cross-ref 消费方** | 谁消费本技能？ | `grep -rn "<本技能名>" ~/.workbuddy/skills/*/SKILL.md` |
| **跨宿主** | 若在 cross_host_skills.json 注册 → 改后须分发 | `python ~/.workbuddy/skills/skill-sync/references/skill_sync.py --execute` |
